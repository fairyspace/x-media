### 一、 核心模块设计（你需要补充和改造的部分）

基于你的知识库总结，系统需要分为 **前端交互层、Agent 策略层、后端调度层、AI 模型层**。

#### 1. 前端层：无限画布与上下文感知 (Canvas UI)
*   **开源项目已提供**：基础的无限画布、节点拖拽、多图层、素材库。
*   **你需要设计的模块**：
    *   **Context Provider (画布上下文)**：实时捕获画布上选中的资产（如：一张杯子图、一段文案），将其序列化注入到 Agent 的 Prompt 中。
    *   **Spec Snapshot 面板**：在侧边栏设计一个“结构化参数面板”，展示当前任务的 JSON Spec（如：`{duration: 12s, style: "轻松", platform: "TikTok"}`），允许用户手动微调。
    *   **分镜/时间轴组件**：针对视频生成，设计类似 Runway 的多镜头轨道，支持首尾帧预览和局部修改。

#### 2. Agent 策略层：槽位补全与 Validator (核心壁垒)
这是你知识库中提到的最核心的“隐藏策略”，需要独立设计为一个微服务或中间件。
*   **意图与槽位提取 (Slot Extraction)**：
    *   用户输入：“帮我生成 12s 广告，适合上班族”。
    *   LLM 提取：`{"duration": 12, "target_audience": "上班族", "missing": ["brand_name", "product_selling_point"]}`。
*   **确定性 Validator (校验器)**：
    *   定义规则引擎：例如 `if (has_voiceover == true) { require(brand_name) }`。
    *   如果校验失败，Agent 不触发下游生成，而是向画布发送一个“交互式卡片”，要求用户补全缺失的“业务槽位”。
*   **视觉槽位解析**：调用视觉大模型（如 Llava / Qwen-VL）分析用户上传的杯子图，自动填入 `{"material": "陶瓷", "color": "白色", "has_logo": false}`。

#### 3. 后端调度层：计费与异步队列 (Billing & Queue)
*   **开源项目已提供**：Redis 异步队列、Go Worker 并发控制。
*   **你需要设计的模块**：
    *   **Quota & Billing 服务**：实现你提到的“预占（Reserve）机制”。在任务进入 Redis 队列前，先冻结用户对应的 Credits/Tapies。如果生成失败（如模型超时、违规词拦截），触发回滚释放额度。
    *   **成本预估器**：根据 `Spec Snapshot` 中的时长、分辨率、是否多版本，调用计费公式，在前端生成前弹出“预计消耗 XX 额度”的确认框。
    *   **Pipeline 编排引擎**：将用户的 Spec 转化为具体的模型调用链。例如：`LLM写脚本 -> 图像模型生成分镜 -> 视频模型图生视频 -> TTS配音 -> FFmpeg合成`。

#### 4. AI 模型网关层 (AI Gateway)
*   **渠道管理**：利用开源项目的后台，配置 Kling、Runway、Sora、Midjourney 等 API 渠道。
*   **ComfyUI 融合**：对于复杂的图像/视频预处理（如抠图、换脸、ControlNet 姿态控制），建议在后端部署一个 **ComfyUI API 服务**。你的 Go 后端将参数转化为 ComfyUI 的 Workflow JSON 并下发执行，这比直接调用黑盒 API 具备更高的可控性。

### 二、 基于 `open-ai-canvas` 的落地改造指南

不要从头写代码，直接 Fork `ddcat-ai/open-ai-canvas`，按以下步骤改造：

#### Step 1: 环境部署与跑通 MVP
1.  **一键部署**：使用项目提供的 `install-server.sh` 在云服务器（推荐 Ubuntu + 8C16G）部署 Docker 环境。
2.  **配置渠道**：在管理后台配置你的 LLM API（用于写脚本和 Agent 对话）和 视频生成 API（如 Kling/可图）。
3.  **跑通基础闭环**：在画布上传一张图，输入 Prompt，测试异步任务队列是否能成功生成视频并回显到画布。

#### Step 2: 注入 Agent 槽位逻辑 (改造 Backend & Web)
*   **修改 `canvas-agent` 目录**：将原本简单的对话 Agent，替换为你设计的 **“广告导演 Agent”**。
*   **引入 System Prompt**：在 Agent 初始化时，注入你知识库中的 System Prompt（包含产品风格规范、合规规则、如何提问补槽位）。
*   **拦截生成请求**：在 Go 后端的 `CreateTask` 接口前增加一个拦截器，校验 `Spec Snapshot` 是否满足 Validator 的最低可交付标准，不满足则返回特定的 Error Code，前端据此弹出补全表单。

#### Step 3: 引入节点化工作流 (参考 Vibe-Workflow / ComfyUI)
*   当产品度过 MVP 阶段，专业用户会需要更细粒度的控制。
*   你可以参考知识库中的 **Vibe-Workflow**，在前端引入 Node-based 编辑器。
*   将后端的线性任务拆解为“节点”（如：LLM节点、生图节点、运镜控制节点），让用户可以在画布上像连线一样自定义 Pipeline。

### 三、 从零到一实施路线图 (Roadmap)

#### Phase 1: 核心 MVP (第 1-2 个月)
*   **目标**：实现“对话/画布 -> 参数收集 -> 单镜头视频生成”闭环。
*   **动作**：
    *   部署 `open-ai-canvas`。
    *   实现基础的 Spec Snapshot（JSON 结构化参数）。
    *   打通 1-2 个主流视频生成模型（如 Kling API）。
    *   实现基础的额度扣减逻辑。

#### Phase 2: Agent 智能化与 Validator (第 3-4 个月)
*   **目标**：让系统像一个真正的“广告制片人”一样工作。
*   **动作**：
    *   上线**确定性 Validator**，实现缺失字段（如没品牌名无法做口播）的自动拦截与追问。
    *   实现**视觉槽位提取**（自动识别上传图片的材质、场景）。
    *   上线**预占（Reserve）计费系统**，避免并发跑爆账单。

#### Phase 3: 影视级工作流与一致性控制 (第 5-6 个月)
*   **目标**：解决 AI 视频最大的痛点——“角色与场景一致性”。
*   **动作**：
    *   开发**角色卡 (Character Card)** 系统，利用 IP-Adapter / 换脸技术锁定模特形象。
    *   开发**3D 导演台 / 控制图回写**功能（利用 ControlNet 控制运镜和动作）。
    *   引入 **ComfyUI** 作为底层图像处理引擎，支持复杂的局部重绘和背景分割。

#### Phase 4: 商业化与生态 (第 6 个月以后)
*   **目标**：对标 Runway / Framia Pro，建立壁垒。
*   **动作**：
    *   开放模板市场（用户可保存自己的 Spec 和 Pipeline 为模板）。
    *   支持多用户协作、资产库共享。
    *   针对特定行业（如电商出海、短剧制作）推出垂直 Agent。

### 四、 关键技术难点与避坑指南

1.  **视频生成的时间一致性问题**
    *   *坑*：直接文生视频，人物长相和衣服每帧都在变。
    *   *解法*：必须采用 **“首尾帧控制 + 角色参考图 (Reference Image) + 运镜提示词”** 的组合拳。在 Spec 中强制要求用户上传或生成一张“基准图”，后续所有镜头基于此图进行 Image-to-Video 生成。
2.  **长文本/多镜头脚本的 JSON 幻觉**
    *   *坑*：让 LLM 直接输出包含 10 个镜头的复杂 JSON，极易格式错误或漏字段。
    *   *解法*：采用 **Step-by-Step 生成**。先让 LLM 生成大纲，再逐个镜头生成详细的 Prompt 和运镜参数；或者使用强约束的 Schema (如 Pydantic / Zod) 配合 LLM 的 Function Calling 功能。
3.  **大文件与 OSS 同步**
    *   *坑*：视频文件大，前端直接上传到后端会导致内存溢出和超时。
    *   *解法*：利用开源项目已支持的 **私有 OSS 直传** 功能。前端获取临时签名 URL，直接传至 S3/OSS，后端只保存 OSS 路径，极大减轻服务器带宽压力。

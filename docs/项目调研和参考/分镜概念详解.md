# 分镜业务概念详解

Created: 2026-07-30
Status: Reference

> 本文档面向刚接触 x-media 项目、对"分镜"等影视业务概念不熟悉的开发者，结合项目现有设计稿讲清楚分镜到底指什么、在系统里怎么落地。

---

## 1. 先讲清楚：分镜是什么（影视行业通用概念）

**分镜（Storyboard）** 是影视、动画、广告制作中的一个专业术语，可以理解为"把一段连续的视频，拆成一格一格的画面单元"。

打一个最直观的比方：**漫画是分格的**——每一格画一幕，按从左到右、从上到下的顺序读下去就是一个完整故事。分镜就是视频版的"漫画分格"：把一段视频拆成若干个有序的镜头单元，每个单元描述"这一段画面长什么样、拍多久、有什么旁白/对白"。

一个分镜通常包含的信息：

| 要素 | 说明 | 例子 |
|------|------|------|
| 画面内容 | 这个镜头里出现什么 | "主角小明走进太空站走廊" |
| 景别 | 镜头的远近（特写/中景/远景） | 特写 |
| 镜头运动 | 摄像机怎么动（推/拉/摇/移/固定） | 缓慢推进 |
| 时长 | 这个镜头持续多久 | 3 秒 |
| 旁白/对白 | 这一段的声音内容 | "欢迎回家，指挥官" |
| 序号 | 第几个镜头 | 镜头3 |

**为什么要分镜**：因为一段完整视频不是一气呵成拍出来的，而是由一个个镜头剪辑拼接而成。先做分镜，相当于先画好"施工图纸"，再逐镜头去生成/拍摄，最后按顺序拼成成片。这对 AI 视频生成尤其重要——当前的视频模型一次只能生成几秒的片段，长视频必须拆成镜头逐个生成再拼接。

## 2. 在 x-media 项目中，"分镜"具体指什么

x-media 是一个面向影视/短剧/广告场景的 AI 视频工作台（见 `docs/README.md` 第 10 行）。项目把"分镜"这个影视概念落地成了画布上的一个**节点类型**和一套**时间线视图**。

具体有三层含义：

### 2.1 分镜是一种画布节点类型（type='storyboard'）

在画布模块（`docs/[02]画布模块/README.md` 节点类型详解表）中，`storyboard` 是一种节点类型，叫做"分镜帧"。它的 `data` JSON 结构是：

```json
{
  "asset_id": 789,
  "duration_ms": 3000,
  "caption": "镜头3",
  "transcript": "旁白文本"
}
```

- `asset_id`：这个分镜帧对应的画面素材（一张代表图，或一段已生成的视频）
- `duration_ms`：这个镜头的时长（毫秒），3000 = 3 秒
- `caption`：镜头标题/序号，如"镜头3-特写"
- `transcript`：旁白/字幕文本

也就是说，**画布上的一个分镜节点 = 视频成片中的一个镜头单元**。

### 2.2 分镜是视频的时间线组织方式

画布节点表 `pms_canvas_node` 有两个专门为分镜设计的字段（见 `docs/[02]画布模块/README.md`）：

- `sort_order`（排序序号）：分镜在时间线上的排列顺序（1, 2, 3...）。非分镜节点为 NULL。
- `group_id`（所属分镜组）：同一组分镜共享一个 group_id，表示"这几帧属于同一组分镜"。

画布还提供了**分镜视图接口**（`docs/[02]画布模块/README.md` 3.5 节）：

| 方法 | 路径 | 说明 |
|------|------|------|
| `GET` | `/api/v1/projects/{id}/storyboard` | 获取分镜列表（按 sort_order 排序） |
| `PUT` | `/api/v1/projects/{id}/storyboard/reorder` | 重新排序分镜 |

用户可以在画布上自由摆放节点（空间布局），也可以切到"分镜视图"按时间顺序排列镜头（时间线布局）。这就把"无限画布的自由编辑"和"视频的线性时序"统一了起来。

### 2.3 分镜是连线的一种语义

画布连线表 `pms_canvas_edge` 的 `type` 字段（见 `docs/[02]画布模块/README.md` 表3）定义了三种连线：

- `flow`：普通数据流连线（实线箭头）
- `timeline`：**时间线连线**（虚线，带方向箭头）——表达"这个分镜 → 接到下一个分镜"
- `reference`：参考引用连线（浅色虚线，双向）

`timeline` 类型的连线就是用来把分镜帧按播放顺序串起来的。

### 2.4 分镜组（group_id）

分镜组是把若干相关分镜帧归到同一组的**逻辑标签**，体现在节点表的 `group_id` 字段（`docs/[02]画布模块/README.md` 表2）：

- `group_id VARCHAR(64)`：项目内自定义字符串，不是数据库外键
- 可空：`NULL` = 不属于任何分镜组；非 `NULL` = 同组节点共享同一个 group_id

**业务含义**：分镜组是一个**归集标签**，不是"故事里的一个段落"。它标记"这些镜头是在哪拍的/哪生成的"，与"它们在成片里什么位置"无关。对应影视制作的两阶段：

- **拍摄/生成阶段（归集）**：同场景的镜头集中拍、集中生成（场地/灯光/演员一次搞定，效率高），打上同一个标签（如"火山"）——不管它们在故事里是开头还是结尾。
- **剪辑/拼接阶段（取用编排）**：按故事流程从各标签池取镜头，用 `sort_order` 编排播放顺序。火山场景的某个镜头可能用于开头，另一个用于结尾。

所以分镜组管"归集归属"，`sort_order` 管"播放顺序"，两者解耦。

**与 sort_order 的关系（两者正交）**：

| 字段 | 维度 | 作用 |
|------|------|------|
| `group_id` | 组织维度 | 这些镜头属于同一组（同一场景/序列） |
| `sort_order` | 播放维度 | 第几个播放（时间线全局排序） |

同一分镜组的镜头不一定在时间线上连续播放——一个场景的镜头可能被剪辑打散到不同位置，所以分组是组织归属，排序是播放顺序。

#### 业务作用（设计意图）

1. **按场景归集镜头（与播放解耦）**：拍摄/生成阶段按场景集中归集（效率高），剪辑阶段再按故事流程取用编排。分镜组是归集维度的标签，不是故事段落——同组镜头可能散落在成片不同位置。
2. **场景内统一设定复用**：同组镜头共享场景设定（同一地点/光线/角色），整组引用相同参考图与角色卡，保证场景内视觉一致性。
3. **批量生成与成本预估**：一个场景的镜头一起规划、一起提交，便于整组成本预估和进度追踪。
4. **版本与回滚粒度**：某场景不满意可整组重做，不影响其他场景。
5. **协作分工**：团队按场景（分镜组）分配负责人。

#### 当前实现实际能做到的

`group_id` 现在只是字符串标签（无外键、无组级元数据、无专门接口），所以：

- ✅ 能做：按组查询过滤（`WHERE group_id=?`）、前端分组折叠展示
- ❌ 暂未支持：整组生成、组级元数据（组名/组状态/组封面）、组级成本预估、组级回滚

即分镜组目前是**"字段预留了分组能力，业务流程尚未跟上"**的半成品状态。要做实需补：组级接口、组级生成入口、可选的组级元数据表。

> 注：文档目前对分镜组的描述仅限 `group_id` 字段定义，未提供分镜组的专门接口（分镜接口只有 `GET /storyboard` 列表和 `PUT /storyboard/reorder` 排序）。若后续需要支持整组生成、整组调整等业务，可能需补充对应设计。

## 3. 容易混淆的概念辨析

新人最容易把"分镜""镜头""场景""节点""Spec"搞混，这里逐个厘清：

### 3.1 分镜 vs 镜头

- **镜头（Shot）**：摄像机从开机到停机拍下来的一段连续画面，是物理拍摄概念。
- **分镜（Storyboard/分镜帧）**：对镜头的预先规划和描述，是创作/设计概念。

在本项目里，**一个分镜节点对应最终成片中的一个镜头**。前期它是"计划"（caption + 时长 + 旁白），生成完成后它挂上 `asset_id` 变成"已实现的镜头"。

### 3.2 分镜 vs 场景

- **场景（Scene）**：故事发生的地点/环境，如"太空站走廊""咖啡馆"。一个场景里可以有多个镜头。
- **分镜**：场景里的具体镜头单元。

项目里场景通常用 `text` 节点（场景描述）或 `reference` 节点（场景参考图）表达，分镜节点引用这些素材来生成画面。

### 3.3 分镜 vs 节点

- **节点（Node）**：画布上所有元素的统称，包括素材节点、文本节点、AI 生成节点、**分镜节点**、角色卡、参考图。
- **分镜**：是节点的一种类型（`type='storyboard'`）。

即：分镜 ⊂ 节点。一个画布项目里可能同时有图片、文字、分镜帧等多种节点。

### 3.4 分镜 vs Spec

这是最容易混淆的一对，见 `docs/[03]Agent策略模块/README.md` 核心概念速查表：

| 概念 | 含义 | 类比 |
|------|------|------|
| **Spec** | 结构化生成参数 | 拍电影的"分镜脚本" |
| **Slot** | Spec 中的一个参数 | 脚本里的"景别""时长""风格" |

- **Spec**：一次 AI 生成请求的完整结构化参数（用什么模型、生成什么、参考谁、参数多少），存在 `pms_agent_spec` 表。它是"给 AI 下达的施工指令"。
- **分镜**：画布上视频的时间线组织单元，是"成片的镜头骨架"。

关系：一个 Spec 可以生成一个分镜帧（单镜头生成），也可以生成一整组分镜（多镜头批量生成）。Agent 模块的 `spec_type` 里专门有 `storyboard` 这一类型，表示"生成分镜脚本"这种任务。Spec 里的 `storyboard_index` 槽位用于指明"这次生成对应第几个分镜"。

## 4. 分镜在系统里的完整数据结构

把上面散落的信息汇总成一张全景图：

```
画布项目 (pms_canvas_project)
  "太空站对决短片"
       │
       ├── 节点 (pms_canvas_node)
       │     ├── text 节点: 场景描述 "太空站走廊"
       │     ├── character 节点: 角色 "小明"
       │     ├── reference 节点: 参考图（风格/构图）
       │     ├── ai_gen 节点: AI生成面板（prompt+model）
       │     └── storyboard 节点（分镜帧）★
       │           data: {asset_id, duration_ms, caption, transcript}
       │           sort_order: 1, 2, 3...（时间顺序）
       │           group_id: 同组分镜共享
       │
       └── 连线 (pms_canvas_edge)
             ├── type='flow': 参考图 → 生成任务（数据流）
             ├── type='timeline': 分镜1 → 分镜2（时间线）★
             └── type='reference': 双向引用
```

带 ★ 的就是分镜相关的部分。一个分镜帧本质上是一个"有顺序、有时长、有旁白、挂着一个画面素材"的节点。

## 5. 分镜的完整使用流程

结合项目文档，一个典型的分镜创作流程是这样的：

```
1. 灵感阶段
   用户在画布上放文本节点写剧本大纲、放参考图定风格、放角色卡定角色
        │
        ▼
2. 规划分镜（两种方式）
   方式A（手动）：用户一个个创建 storyboard 节点，填 caption/时长/旁白
   方式B（Agent 自动）：用户说"把这段大纲拆成 8 个分镜"
        │  → Agent 模块 spec_type='storyboard' 提取
        │  → LLM 输出分镜列表（注意踩坑点：不能让 LLM 一次输出 10 个镜头的
        │     JSON，要先出大纲再逐镜头生成，见 tapNow.md 第224行）
        ▼
3. 逐镜头生成画面
   对每个分镜帧，框选相关节点（角色卡+参考图+场景文本）→ 创建快照
        │  → 提取 Spec（含 storyboard_index 指明第几镜）
        │  → Agent 校验槽位（景别？时长？风格？角色一致性基准图？）
        │  → 提交任务调度模块 → AI 网关调模型生成
        │  → 结果回写：生成视频挂到该分镜帧的 asset_id
        ▼
4. 排序与预览
   GET /api/v1/projects/{id}/storyboard 按时间线预览
   拖拽调整顺序 → PUT /api/v1/projects/{id}/storyboard/reorder
        ▼
5. 拼接成片
   按分镜顺序拼接各镜头视频 + 叠加字幕/配音 → 导出
```

**关键设计点**（来自 `docs/[02]画布模块/README.md` 第536行）：

> 快照机制让用户在 AI 生成过程中 **继续编辑画布**，不会影响正在执行的任务。

也就是说，用户给"分镜3"提交了生成任务后，可以马上回去编辑"分镜4"的分镜帧，两者互不干扰——因为每次生成都冻结了一个快照。

## 6. 为什么本项目要用"分镜"模型

这是核心设计决策，原因有三：

### 6.1 视频创作天然是镜头序列，不是单段

当前 AI 视频模型（Kling、Sora、SVD 等）一次只能生成 5-10 秒的片段。做一部 60 秒的广告或几分钟的短剧，必须拆成多个镜头逐个生成再拼接。分镜就是这个"拆"和"拼"的组织单元。竞品 open-ai-canvas 也用独立的 Shot/Unit 模型来做这件事（见 `docs/[02]画布模块/README.md` 竞品对比表）。

### 6.2 支持逐镜头调整，而非黑盒整片重生成

如果用户只对"分镜5"不满意，只需重新生成第 5 个镜头，不用整片重来。这正是"业务可控：可校验、可计费、可回滚"（见 `docs/README.md` 核心价值）的体现。每个分镜帧独立有自己的 `asset_id` 和生成任务记录。

### 6.3 解决角色一致性问题

`docs/项目调研和参考/tapNow.md` 第220-221行专门提到这个坑：

> 视频角色一致性：直接文生视频，人物长相衣服每帧都在变。解法：**首尾帧 + 角色参考图 + 运镜提示词三件套**。Spec 里强制要一张基准图，后续镜头全走图生视频。

分镜模型让每个镜头都能引用同一个角色卡（`character` 节点）作为参考，保证整片角色长相一致——这是单纯"输入一段文字出整片视频"做不到的。

## 7. 画布节点如何参与生成

### 7.1 节点是平级的素材与配置单元

一个项目（`pms_canvas_project`）下所有节点都是 `pms_canvas_node` 表里**平级的一行**，按 `type` 区分用途，全部直接挂在 `project_id` 下：

```
项目 (pms_canvas_project)
  └── 平级节点们 (pms_canvas_node，一行一个，全部直接属于项目)
        ├── character  角色卡（角色设定，供各镜头引用保持一致性）
        ├── text       剧本说明/场景描述
        ├── reference  风格/构图参考图
        ├── ai_gen     AI 生成面板（承载 model/prompt/params）
        ├── asset      素材（已生成的图片/视频）
        └── storyboard 分镜1 / 分镜2 / 分镜3 ...（按时间线排列的镜头）
```

分镜的时间顺序靠 `sort_order` 字段 + `timeline` 类型连线组织；`parent_node_id` 仅作为可选的辅助嵌套（如角色卡内嵌参考图），不是分镜结构的核心。

### 7.2 生成靠"框选 + 快照提取"，不靠连线接输出节点

x-media 的画布是**框选驱动**的，不是 ComfyUI 那种"连线编程"模型——**没有预先存在的"输出节点"这种节点类型**。生成入口是：用户框选若干节点 → 后端遍历选中节点**按 type 提取 Spec**：

| 被框选的节点 type | 提取到 Spec 的位置 |
|------------------|-------------------|
| `character` 角色卡 | `spec.characters[]` |
| `text` 剧本说明 | `spec.scene_description` |
| `reference` / `asset` 参考图 | `spec.references[]` |
| `ai_gen` 生成面板 | `spec.generation_params`（model/prompt/params） |
| `storyboard` 分镜帧 | `caption` / `transcript` 作为上下文，`storyboard_index` 指明第几镜 |

也就是说，角色卡、剧本说明这些节点**通过被框选进入快照**来参与生成，按 type 被自动归位到 Spec 的对应字段，而不是靠连线接到某个输出节点。

### 7.3 "输出"是生成后新建的 asset 节点

生成结果不写入某个预置输出节点，而是由任务模块回调 `POST /internal/projects/{id}/nodes`，**作为一个新的 `asset` 节点插回画布**。如果是为某个分镜帧生成，结果挂到该分镜帧的 `data.asset_id` 上——分镜帧即从"计划"（caption + 时长 + 旁白）变成"已实现的镜头"（挂上了真实视频素材）。

### 7.4 连线的真实用途

连线（`pms_canvas_edge`）不是生成的硬性前提，而是用来表达节点间的关系：

| 连线 type | 用途 |
|-----------|------|
| `flow` 数据流 | 可视化表达"参考图喂给生成任务"，`ai_gen` 节点有 `input_reference`/`input_prompt` 端口可连接 |
| `timeline` 时间线 | 串联分镜帧的播放顺序 |
| `reference` 引用 | 表达素材引用关系（双向） |

连线作为数据依赖上下文会一并传给 Agent 模块，但 Spec 的核心提取逻辑是按节点 type 遍历，不依赖连线。

### 7.5 一次生成的完整图示

```
用户针对"分镜2（主角特写）"生成画面：
  框选 [角色卡-小明] + [科幻风格参考图] + [剧本说明文本] + [分镜2节点]
       ↓ 创建快照（冻结当前画布状态）
       ↓ 按 type 提取 Spec（storyboard_index=2 指明第几镜）
       ↓ Agent 校验槽位（景别？时长？角色基准图？）
       ↓ 提交任务 → AI 生成这一个镜头（几秒）
       ↓ 生成结果作为新 asset 节点插回画布，并挂到 分镜2.asset_id

所有分镜帧各自生成完毕后：
  分镜1(3s) → 分镜2(2s) → 分镜3(4s) → ...  按时间线拼接 → 完整视频
```

> 依据：`docs/[02]画布模块/README.md` 表注释"每个节点一行"、4.2 快照提取逻辑（遍历选中节点按 type 提取）、生成结果作为新 asset 节点插入画布（任务回调 `POST /internal/projects/{id}/nodes`）。

## 8. 一句话总结

**分镜 = 把视频拆成有序的镜头单元，每个单元是一帧画面 + 时长 + 旁白。在 x-media 里，它是 `storyboard` 类型的画布节点，用 `sort_order` 排时间线、用 `timeline` 连线串顺序、用 Spec 逐镜头驱动 AI 生成。它是"无限画布的自由编辑"和"视频的线性时序"之间的桥梁。**
